Flow Report · Try-On Engine Routing

Saree try-ons on Fashn.ai, everything else on RunPod

Sarees are routed to the hosted Fashn.ai API in the storefront widget and both Studio flows. Every other garment keeps using the RunPod FASHN VTON 1.5 endpoint, and no other flow (including OpenAI infographics) is changed.

1. Routing decision

The same decision runs at submit time in all three flows. It is made once, then carried by the job ID.

Try-on requestwidget, AI Studio or Garment Studio
↓
Prompt or product title mentions saree / sari?
↓
Yes
Fashn.ai onlytryon-max + nivi-drape prompt, retry once on 429 / 5xx / network error. Never RunPod.
No
RunPod (unchanged)tops, bottoms, dresses, lehenga, everything else

In the Studio wizard, choosing Saree under "What are you selling?" sends product_type=saree and decides the engine; any other choice stays on RunPod. Where no product type is sent (widget, older callers) detection is a case-insensitive match on sarees? / saris? in the prompt or product title. The Accessories workflow never goes to Fashn.

2. Storefront widget flow

Submit and poll are separate short requests, so no single call risks the Shopify App Proxy timeout. The widget passes job_id through without reading it.

  1. Shopper · widgetShopper uploads a photo and clicks Try On. Widget POSTs to /api/tryon.
  2. Shopify app · api.tryon.jsxVerifies the proxy signature and forwards to PHP POST /tryon. Unchanged.
  3. PHP · TryOnController::submitMerchant auth and plan limit check, then image prep. Runs shouldUseFashn() on the clothing prompt and product_title.
  4. Saree → FashnSareeRouting::submitFashn() sends the person and garment images to Fashn tryon-max with a nivi-style drape prompt. Returns fs_<id>.
  5. Other → RunPodExisting RunpodVtonClient::submitRun(). Returns the plain RunPod job ID.
  6. WidgetReceives {status: processing, job_id} and polls /api/tryon-status every 2.5s, up to 190s.
  7. PHP · TryOnController::pollStatusSareeRouting::checkStatus(job_id) checks the right engine exactly once per request.
  8. PHPOn completion: save the image, mark the session complete, increment the merchant's count, log analytics. Responds {status: completed, result_image}. Identical for both engines.

4. Job ID lifecycle

The engine is encoded in the job ID, so the stateless poll endpoints know who to ask without new query params, columns or widget changes.

fs_123a87r9-4129-4bb3-…-u1
Fashn prefix fs_ is stripped before calling Fashn's status API.
a1b2c3d4-….-u1
RunPod no prefix. Jobs already running at rollout keep resolving.

Both engines return the same {job_status, image_bytes, error_details} shape from a status check, so the existing save, analytics and infographic code is engine-agnostic.

5. Failure handling

SituationBehavior
Fashn submit fails with network error, 429 or 5xxRetry once after 1.5s. If it still fails, the user sees the normal try-on error (429 → "temporarily unavailable").
Fashn rejects the request (4xx)No retry. Session marked failed with the raw error logged.
Fashn job fails during generationPoll returns failed. Session marked failed, analytics logs tryon_failed.
Status check has a transient errorTreated as still processing. The client polls again.
Studio job never resolvesExisting 3-minute timeout marks it failed.
FASHN_API_KEY blankSaree try-ons fail with a "not configured" error and are logged. They never fall back to RunPod.
Fashn enabled, RunPod not configuredSarees still work. Non-sarees get the existing "not configured" 503.
!

No fallback to RunPod for sarees. RunPod cannot process category=saree and drapes sarees poorly, as a stitched one-piece dress, so a Fashn failure surfaces as an error instead of a silently worse result.
